# Приклад: «Три справи» — локальний застосунок

Навчальний мініприклад документів Lite. Усі рішення нижче — умовні; дослідження, реалізація та тести не виконувались. ID належать лише цьому прикладу. Розділи можна перенести у відповідні п’ять файлів.

## PRODUCT

Ідея: дорослий користувач обирає до трьох справ, щоб бачити невеликий список пріоритетів. Назва робоча. Перша платформа — Android, мова — українська. Дані лише на пристрої, акаунтів немає. Бюджет — до двох тижнів роботи однієї людини; це обмеження планування, не оцінка готовності.

OBJ-001: користувач самостійно створює й позначає виконаною першу справу. Гіпотеза: щонайменше 4 з 5 учасників першого тесту роблять це за 60 секунд без підказки. Спосіб — спостереження за прототипом; за невдачі переглянути підписи та основну дію. Це якісний малий тест, не ринкова валідація.

## REQUIREMENTS

Шлях: відкрити → додати справу → побачити у списку → позначити виконаною.
MVP: локальний список максимум із трьох записів, додавання, перемикання виконання, видалення, збереження. Later: дати, нагадування, синхронізація, статистика. Немає автоматичного скидання опівночі. Виконані записи займають місце, доки їх не видалено.

REQ-001 — додавання; Must, OBJ-001. Без додавання немає основного шляху.
- AC-001: при двох записах введення «Купити хліб» і натискання «Додати» створює третій невиконаний запис та очищує ввід після успішного запису.
- AC-002: при трьох записах додавання четвертого неможливе, показано «Максимум 3 справи»; список не змінюється. Порожній після trim текст не додається; довжина обмежена 80 символами за правилом підрахунку, визначеним в UI-контракті.

REQ-002 — виконання та видалення; Must, OBJ-001. Потрібні для завершення й повторення шляху.
- AC-003: натискання checkbox перемикає виконання відповідного запису, не змінюючи інші. Повторне натискання повертає стан.
- AC-004: підтверджене видалення прибирає тільки вибраний запис; скасування лишає список без змін.

NFR-001 — надійність локального списку; Must, OBJ-001.
- AC-005: після успішної зміни, примусового закриття й запуску список, порядок і прапорці відновлені без мережі.
- AC-006: за ін’єктованої помилки запису UI показує повідомлення, не підтверджує успіх і зберігає попередній стан; введений текст доступний для повтору.

## DESIGN

UX-001: один екран, поле, кнопка додавання, список. Empty — «Додайте першу справу»; loading — коротке завантаження сховища без активного вводу; error — пояснення й повтор; offline — звичайна робота. Checkbox має текстову мітку; стан не передається лише кольором. Видалення через кнопку та підтвердження. Орієнтація портретна; збільшений системний шрифт перевіряється вручну.

UI-контракт: обрізати зовнішні пробіли; ліміт 80 Unicode code points після trim, emoji-послідовність може займати кілька позицій. UI показує лічильник за тим самим правилом.

Дані: Task(id: унікальний string, title: string, completed: boolean, position: integer). Схема v1, до трьох записів. Видалення — локально без undo; дані існують до видалення користувачем або очищення даних застосунку. Немає експорту, зовнішніх SDK чи передачі даних; застосунок не запитує дозволів. Backup ОС потребує явного рішення до випуску (Q-002).

ADR-001 — proposed: UI → логіка списку → репозиторій. Порівняно з прямим записом із UI, окремий репозиторій дозволяє перевірити помилки. Backend відхилено через відсутність sync у scope. Конкретне сховище й атомарність запису обрати після Q-001; технічний стек ще не погоджено. Не запускати реалізацію за цим прикладом без цього рішення.
