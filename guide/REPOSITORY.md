# Структура репозиторію продукту

```text
my-product/
├── README.md                 # як запустити продукт
├── AGENTS.md                 # правила coding agents
├── docs/
│   ├── PRODUCT.md
│   ├── REQUIREMENTS.md
│   ├── DESIGN.md
│   ├── DELIVERY.md
│   ├── STATE.md
│   ├── modules/              # лише активні модулі
│   ├── adr/                  # опційно, якщо ADR виросли з DESIGN
│   ├── tasks/                # опційно, якщо задачі виросли з DELIVERY
│   ├── research/             # нотатки і джерела без персональних даних
│   └── evidence/             # звіти, знімки, результати перевірок
├── app/                      # код за конвенціями обраного стеку
├── tests/                    # або розміщення тестів за конвенціями стеку
├── assets/                   # графіка, звук, ліцензії
└── scripts/                  # відтворювані команди, коли потрібні
```

Це логічна схема, не вимога створити порожні папки. Після вибору стеку використовуйте його стандартну структуру: наприклад, директорії native-проєкту або рушія можуть замінити `app/`. Опишіть фактичні шляхи у README.

Для MVP достатньо п’яти docs-файлів. При винесенні ADR/TASK в окремий файл залиште в основному документі короткий індекс і відносне посилання; видаліть дубльований текст.

Робочий AGENTS має діяти на код продукту. Сам комплект зберігайте поза цим кодом або у `tooling/discovery-kit/`; його шаблон AGENTS не має випадково стати активними інструкціями.

Не комітьте секрети, реальні користувацькі дані й локальні сертифікати. При появі конфігурації додайте `.env.example` лише з назвами й безпечними прикладами та налаштуйте `.gitignore` під фактичний стек. Правила збірки й перевірок записуйте після їх реального виконання, а не з припущень.
