# Вимоги, джерела істини та перевірки

## ID й посилання

Використовуйте стабільні ID: `OBJ-001` ціль, `REQ-001` поведінка, `NFR-001` якість, `AC-001` критерій приймання, `UX-001` сценарій/екран, `ADR-001` рішення, `TASK-001` задача, `TEST-001` перевірка, `Q-001` питання, `RISK-001` ризик, `CHG-001` зміна.

Кожен ID визначається один раз, у заголовку `## REQ-001 — Назва` або у відповідній таблиці. Повторне згадування — посилання, не нове визначення. Не перенумеровуйте й не використовуйте повторно видалені ID: позначте `retired` і причину.

Обов’язковий ланцюг: `OBJ → REQ/NFR → AC → TASK → TEST → доказ`. UX та ADR додавайте лише там, де вони застосовні. Тест може покривати кілька AC, а задача — кілька вимог, але зв’язки мають бути явними. Spike без продуктової вимоги посилається на Q або RISK і має умову завершення.

## Джерела істини

| Інформація | Де редагувати |
|---|---|
| Аудиторія, цілі, гіпотези | PRODUCT |
| Scope, пріоритет, поведінка, AC, NFR | REQUIREMENTS |
| UX, дані, контракти, ADR | DESIGN або активний модуль за посиланням |
| Задачі, тест-кейси, результати, release | DELIVERY |
| Gates, питання, baseline, журнал змін | STATE |

Таблиця трасування в REQUIREMENTS містить ID й посилання, не копії текстів. AGENTS описує процес, не дублює продуктові вимоги. Якщо код і погоджені вимоги розходяться, зафіксуйте дефект або CHG, не переписуйте вимогу для виправдання коду.

## Перевірка перед G3 та G4

1. У кожного Must REQ/NFR є OBJ, причина, AC; критерії містять спостережуваний результат. Слова «швидкий», «зручний» без міри — прогалина.
2. Кожен AC має TASK і TEST. Запланований TEST достатній для G3; для G4 потрібні результат, середовище й доказ.
3. Немає задач на out-of-scope функції або «сиріт» без вимоги/Q/RISK. Залежності існують, не утворюють циклів; ready не залежить від незавершеного блокера.
4. UX і правила збігаються: наприклад, екран видалення відповідає політиці зберігання. Задокументовані empty/error/offline та відмова в дозволі, якщо застосовно.
5. NFR узгоджені з платформами, пристроями, сховищем та обмеженнями бюджету. Відсутність мережі не суперечить обов’язковій серверній дії.
6. Гра: перемога, нагорода, повтор і save не суперечать одне одному; контент має власника та спосіб перевірки розв’язності.
7. Активні модулі повні в межах MVP. Неактивні мають N/A-причину. Немає невирішених placeholders у частині, яку погоджуємо.
8. ID унікальні в межах проєкту, посилання існують; зміни пройшли impact review. Шаблони й приклади не входять у перевірку ID робочого проєкту.
9. Статуси чесні: `planned` не дорівнює `passed`, макет не є реалізацією, самооцінка AI не є результатом користувацького тесту.

Формат знахідки: `severity: blocker/warning | ID | файли | суперечність | рекомендоване виправлення | власник`. Blocker перешкоджає відповідному gate; warning потребує записаного рішення. Це семантична перевірка людиною/AI; starter kit не містить автоматичного валідатора.

## Управління змінами без бюрократії

Запишіть CHG у STATE: причина → зачеплені ID → вплив на scope/час/дані/тести → рішення власника. Оновіть джерело істини, потім зв’язки й залежні задачі; позначте зачеплені gates stale. Для косметичних правок без зміни поведінки достатньо короткого запису в історії Git. Вимогу, яку прибрали з MVP, перенесіть у Later, зберігши ID та причину.
